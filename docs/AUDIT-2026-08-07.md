# TSDNE audit — 7 August 2026

**Originally audited head:** `47fb889035ed6dbe06a6b422dd5c51779e426091`  
**Original scope:** thirty-nine-family generator, structure/colour/finish separation, candidate selection, responsiveness changes, public-project framing, and the then-separate curation prototype.  
**Resolution status:** updated later on 7 August 2026 after implementation of the shared production runtime and external curation audit.

## Historical purpose

This document records problems identified during the 7 August generator expansion and how they were subsequently resolved. The findings below should be read as production history, not as the current implementation specification.

The original audit judged the expansion from twelve to thirty-nine structural families and the separation of structure, colour, and finish to be a substantial improvement, while identifying several defects that made the planned curation evidence unreliable. The generator later expanded again to **forty-nine families**.

The conceptual conclusion remains unchanged: generator breadth is infrastructure required to make computational abundance experientially credible. It is not the principal originality claim of TSDNE.

## Finding 1 — category-biased candidate pools

### Original problem

The thirty-nine-family `FAMILY_NAMES` list was organised by visual category. The then-current `familySchedule()` chose a random offset and walked the list sequentially, while candidate-pool construction stopped after only a small number of valid candidates. A pool could therefore contain a categorical neighbourhood rather than a broad cross-section of the grammar.

This mattered both for the public artwork and for any curation evidence: a selector cannot demonstrate broad choice if its candidate pool systematically excludes distant visual categories.

### Resolution

The generator now uses one explicit family/category ledger. Family lists and metadata are derived from that ledger, and scheduling is stratified across macro-categories before categories repeat. Automated tests verify that the schedule crosses categories and avoids recently used families while sufficient alternatives exist.

This removes the specific ordered-list bias identified here. It does not imply that the resulting sampling distribution is statistically uniform or that every family receives equal exposure; the public selector is intentionally a production system rather than a balanced experimental sampler.

## Finding 2 — obsolete standalone curation implementation

### Original problem

The first researcher-only branch, `research/curation-instrument-250`, forked before the expanded generator and independently reimplemented generation, validation, candidate-pool construction, selector scoring and history. As the production system evolved, the curation branch became stale and ceased to audit the actual artwork.

A second attempted revision branch inherited the same architectural risk.

### Resolution

Both obsolete curation branches have been deleted.

The replacement architecture centralises all production mechanics in `prototype/src/runtime.js`. Both:

- the public adapter, `prototype/src/main.js`; and
- the private curation adapter, `prototype/src/curation.js`

call this same runtime.

Contract tests prohibit the curation adapter from importing the low-level generator, synthesis/selector, perception, history, WebGL or provenance modules. The invariant is:

> **TSDNE produces; curation observes.**

The curation audit therefore records the real production encounter rather than approximating or reproducing it.

## Finding 3 — absence of real WebGL compilation in CI

### Original problem

Earlier generator tests checked deterministic source generation, declarations, delimiter balance, colour/finish routing and estimated cost, but did not submit emitted GLSL to a real browser WebGL2 compiler/driver.

### Resolution

CI now serves a dedicated no-index diagnostic page and launches headless Chrome using WebGL2/SwiftShader. The diagnostic compiles and renders three variant conditions for every current family while cycling colour and finish regimes.

For implementation commit `447e8e4c99a1ea8f9de66dedc6c47096d2dd1fc0`, the diagnostic reported:

`TSDNE_WEBGL_COMPILE_PASS 147/147`

The ordinary CI run also passed all **37** unit and architectural-contract tests at that historical revision.

This is meaningful executable validation, but it is still a smoke test on one browser/driver configuration. Safari, Firefox, Android, iOS and ordinary hardware remain necessary empirical checks, as does visual inspection of the rendered results.

## Finding 4 — incomplete anti-repetition reset

### Original problem

Persistent perceptual traces and recent-family state were cleared while session-only recent colour modes remained active. The interface therefore claimed to clear anti-repetition memory while one selection state continued to influence the next output.

### Resolution

The shared runtime's clear operation now resets:

- recent perceptual traces;
- recent family state;
- recent colour-mode state;
- pending prefetch state.

The public wording and actual selector state are therefore aligned.

## Finding 5 — explicit visual genealogy

### Original problem

Family names such as `richter-rhythm`, `eggeling-diagonal`, `suprematist-drift`, and `bauhaus-tiles` make visual-historical reference explicit. This is preferable to hiding reference inside an opaque learned corpus, but unexplained names risk reducing specific histories to style labels.

### Current requirement

The project should continue maintaining a visual-grammar genealogy that identifies:

- historical references and the formal problems they contribute;
- procedural/computational precedents such as Truchet tiling, Julia/orbit-trap systems, Apollonian packing, KIFS, ray marching, dynamical fields, phyllotaxis, contour mapping, cellular automata and reprographic techniques;
- the distinction between explicit reference and stylistic imitation;
- the fact that the public runtime uses no learned generative corpus.

The original audit consulted primary museum documentation for Hans Richter, Viking Eggeling and geometric abstraction. Those references remain useful starting points, but the expanded forty-nine-family grammar requires broader documentation.

## Finding 6 — three-axis grammar as evidence, not priority claim

The separation of:

1. structural family;
2. colour mode;
3. reprographic finish

remains useful because perceived abundance depends on more than the count of named families. It operationalises the requirement that successive encounters remain heterogeneous.

It should not be presented as a novel procedural-graphics technique. Its scholarly role is evidentiary and practice-based.

## Revised curation methodology

The earlier proposal for a bounded 250-item study has been superseded.

The current method is an open-ended, practical external audit. The curator may inspect a few or many shaders in one session, close the browser, and continue in a later session. The cumulative browser-local corpus remains available until explicitly exported or cleared.

The curation labels are:

- **OK** — acceptable for TSDNE as-is;
- **not OK** — should not appear in TSDNE as-is;
- **repetitive** — acceptable in itself but too similar to a recent encounter.

This formulation is more useful than the earlier `interesting / not interesting / skip` vocabulary because it maps directly onto the production requirements:

- `not OK` identifies intrinsic failures;
- `repetitive` identifies sequence-level failures;
- `OK + repetitive` identify individually acceptable outputs.

The rating interface is blind to generator diagnostics. The audit record, however, captures exact production state, candidate pools, rejection funnels, perceptual descriptors, hashes, version/build information and recent anti-repetition traces.

No curation label is fed back into generation during collection. Analysis occurs between explicit generator revisions.

See [`CURATION-AUDIT.md`](CURATION-AUDIT.md).

## Paper implications

The production history supports several concrete points without turning TSDNE into a shader-exploration paper:

- perceived abundance is an engineering and aesthetic requirement, not merely a rhetorical assertion;
- the visual grammar expanded repeatedly because early versions converged perceptually;
- structure, colour and surface finish were separated to increase heterogeneous encounters;
- private artistic curation is explicitly separated from public visitor profiling;
- `repetitive` judgements create a direct diagnostic of the anti-repetition metric;
- historical/computational references should be documented rather than hidden;
- browser CI can validate compilation but cannot establish artistic quality or cross-device experience.

The curation corpus should be presented as first-person production evidence within an autobiographical-design/research-through-design process, not as a population-preference dataset.

## Remaining action order

1. use the deployed curation audit in practical sessions;
2. export the corpus periodically;
3. analyse `not OK` and `repetitive` failures separately;
4. make explicit, versioned revisions to weak families, parameter regions, colour/finish combinations, quality thresholds, selector weights or perceptual descriptors;
5. compare later curation epochs where that comparison is informative rather than compulsory;
6. complete real-device/cross-browser and photosensitive-safety review;
7. expand the visual-grammar genealogy;
8. incorporate the production evidence into the journal manuscript without converting TSDNE into an optimisation or recommendation project.
